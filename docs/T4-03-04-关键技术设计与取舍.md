## 1. 系统架构与模块分层

### D1. 两个 FastAPI 服务加前端开发代理，而非直接合并后端（重点）

- **当前方案**：查询服务入口为 `knowledge/api/query_router.py:create_app`（8001），导入服务入口为 `knowledge/api/import_router.py:create_app`（8000）。`frontend/vite.config.ts` 把 `/api/core`、`/api/admin` 分别代理到两端；`frontend/src/services/http.ts` 与 `printcare-api.ts` 是页面统一接口层。
- **适配性**：保留既有查询、上传的独立运行入口，前端仍可用同源路径和 Cookie，不需要为改 UI 同时迁移导入链或数据库连接。
- **替代方案与代价**：单一 FastAPI 可减少开发端口、CORS/代理配置和部署对象，但需合并路由、依赖生命周期、静态页兼容与故障边界；独立 API Gateway 则增加部署与鉴权复杂度。当前代码没有证明这些替代方案带来收益。
- **局限**：两个服务各自依赖配置与进程内任务状态；只要横向扩容或公开部署，就需要重新处理 sticky routing、统一认证和健康检查。

### D2. API/Service/LangGraph/Utils 四层分工（重点）

- **当前方案**：`api/` 负责 HTTP、Cookie、Pydantic 和状态码；`services/` 负责业务用例和持久化时机；`processor/*/main_graph.py` 负责编排节点；`utils/` 适配 Mongo、Milvus、MinIO、模型、任务与 SSE。依赖入口集中在 `knowledge/core/deps.py`。
- **适配性**：例如诊断路由不会直接把模型候选写 Mongo，`DiagnosisService._run_turn` 负责“图结果已验证后才持久化”；这使 HTTP 协议、图节点和会话一致性各有明确位置。
- **替代方案与代价**：把逻辑直接写在路由中开发较快，但难以复用并难以保证非 HTTP 调用仍经过校验；采用完整 DDD/CQRS 可进一步隔离读写，却会超过当前单体演示系统的复杂度。
- **局限**：分层并不完全均匀，查询节点仍会直接使用 `task_util`、`sse_util`，部分旧注释/示例反映的历史实现已不完全等同当前流程。

### B3. 缓存客户端与服务实例

`knowledge/core/deps.py` 用 `cache`/`lru_cache` 复用 Service；`utils/client/ai_clients.py` 和 `storage_clients.py` 延迟、加锁创建模型/存储客户端。它减少同进程重复初始化（尤其本地模型），但配置在进程启动/首次使用后不会自动热更新，且不构成多进程共享连接池或故障转移。

## 2. RAG：检索、融合与重排序

### D4. BGE-M3 稠密 + 稀疏的 Milvus 混合检索（重点）

- **当前方案**：`VectorSearchNode.process` 与 `HyDeSearchNode.process` 都调用 `generate_bge_m3_hybrid_vectors`；`milvus_util.py:create_hybrid_search_requests` 对 dense 使用 `COSINE`、sparse 使用 `IP`，`execute_hybrid_search_query` 以 `WeightedRanker(0.5, 0.5)` 合并。导入链 `BgeEmbeddingChunksNode` 负责写相应向量字段。
- **适配性**：3D 打印资料同时包含型号、错误名、参数和自然语言操作，词项匹配与语义匹配可能互补；在一个 Milvus collection/查询中完成，避免维护第二套检索库。
- **替代方案与代价**：纯 dense 实现更简单但可能丢失精确术语；BM25/Elasticsearch 需新增服务和同步；不同权重、学习排序或多向量字段可能更优，但仓库没有离线评测、召回指标或调参对比作为依据。
- **局限**：0.5/0.5 是当前写死默认，而非测得最佳值；每分支当前请求上限为 5，候选覆盖受限，且清洗/切分质量直接影响检索质量。

### D5. 直接检索 + HyDE 并行，再用 RRF 合并本地候选（重点）

- **当前方案**：`main_graph.py:route_search_branches` 并行调度 `VectorSearchNode` 和 `HyDeSearchNode`。后者先由 LLM 生成假设性技术文档，再检索。`RrfNode.process` 只按 `chunk_id` 以 RRF 合并这两路，默认 `rrf_k=60`、最多 10 项（`query_process/config.py`）。
- **适配性**：原始故障描述可能口语化，HyDE 可提供“可能的手册表达”作为额外检索视角；RRF 不依赖两路原始分数同尺度，适合合并不同查询路径的排名。
- **替代方案与代价**：只保留直接检索可降低一次 LLM 调用、延迟和失败面；把 HyDE 改为 query expansion 或多查询也可行，但会引入更多生成/合并策略。仓库未证明 HyDE 相对这些策略的量化提升。
- **局限**：HyDE 本身依赖外部 LLM，可能超时或生成偏离；其失败会使该分支返回空增量。并行节点曾出现并发写 State 冲突，T3 才改为各自仅返回增量，说明图状态合并需要持续谨慎维护。

### D6. 把 Web 结果留在 RRF 之外、与本地候选一起 Rerank（重点）

- **当前方案**：`RrfNode` 仅处理 `embedding_chunks` 和 `hyde_embedding_chunks`；`RerankNode._merge_multi_source__docs` 随后合并本地 RRF 与 QA 的 `web_search_docs`，使用 `FlagReranker.compute_score`、sigmoid 和断崖截断（默认至少 3、最多 10，gap 默认 0.15）。
- **适配性**：网页搜索返回的是 title/url/snippet，与 Milvus 命中结构和排名语义不同；不把它硬塞入本地 RRF，避免将网页的非同质排名当成向量检索排名。Reranker 以同一问题比较文本，成为两类候选的统一选择点。
- **替代方案与代价**：可让网页先单独过滤或只作补充回答；也可统一用 RRF，但需定义网页排名可信度。使用 cross-encoder 全量候选重排准确性可能更高，代价是本地模型推理延迟与显存/CPU 负担。
- **局限**：断崖和阈值未有离线标注集验证；网页 snippet 天然短且质量由上游搜索决定，进入最终上下文不等于与 K1 本地资料同等可信。

### D7. 设备归属是检索前的服务端过滤，而非 Prompt 约定（重点）

- **当前方案**：`core/devices.py:resolve_supported_device` 当前仅允许 `creality-k1`；查询/导入服务都使用服务端 canonical `device_id`、`device_model`、`item_name`。`milvus_util.py:item_names_filter` 为两个混合检索请求生成 `device_id == ... and item_name in ...`。
- **适配性**：诊断需要避免跨设备资料污染。把条件交给 Milvus 在召回前过滤，强于“让模型忽略无关文档”的软指令。
- **替代方案与代价**：每设备独立 collection 能简化查询条件，但会增加 schema、索引和生命周期管理；只保留文档元数据后过滤则可能先召回错误设备并浪费有限 top-k。
- **局限**：V1 只支持一个设备，真实多设备可扩展性未验证；条件同时依赖正确入库元数据，历史/错误归属数据不会因查询代码自动修复。

### B8. 上下文字符预算与来源“实际入 prompt”语义

`AnswerOutputNode._format_context_sources` 和 `DiagnosisDecisionNode._build_prompt` 都按字符预算裁剪。QA 的 `sources` 仅记录真正装入最终 prompt 的文档，而非全部候选或逐句事实引用。这避免 UI 夸大来源范围，但预算按字符非 token 估算，且 QA 来源未做诊断级的逐句支持校验。

## 3. QA、Web MCP 与来源管理

### D9. QA 允许 Web MCP，但保留来源类型（重点）

- **当前方案**：`WebSearchMcpNode.process` 仅在 `mode='qa'` 时创建 `MCPServerStreamableHttp`，调用 `bailian_web_search`，最多取三个结果；`RerankNode` 将网页规范为 `source_type='web'`、`source_id=url`，本地 chunk 规范为 `source_type='local'`、`source_id='chunk:<id>'`。`SourceReferences.tsx` 用不同标签和链接展示。
- **适配性**：普通问答可利用本地资料以外的实时/补充信息，同时让用户看见资料类型，而不是把网页伪装为设备手册。
- **替代方案与代价**：完全禁用网页可提升可控性但降低开放问答覆盖；把网页单独显示、不送入生成可提升保守性但减少融合价值；引入域名白名单、抓取正文/可信度评分可改善质量，但当前没有这些设施。
- **局限**：网页相关性、可用性和内容安全依赖上游搜索；当前来源卡片说明的是上下文片段，不能宣称网页或本地资料已逐句核验答案。

### B10. 会话历史参与 QA 改写和回答 Prompt

`ItemNameConfirmNode.process` 读取访客所属 `chat_message`，让 LLM 改写问题；`AnswerOutputNode._format_chat_history` 以剩余预算拼入回答 Prompt。它支持连续追问，但历史长度、隐私和早期误解会影响后续生成；当前只有最近窗口与字符预算，未实现摘要、撤销单条记忆或跨会话检索。

## 4. Diagnosis：动态决策、证据校验与安全降级

### D11. 显式 `mode` 复用检索图、在 Rerank 后转入诊断决策（重点）

- **当前方案**：`QueryRequest.mode`、`QueryService.build_diagnosis_graph_state` 和 `main_graph.py` 共同决定分支。诊断复用本地 Vector、HyDE、RRF、Rerank，随后由 `route_after_rerank` 进入 `DiagnosisDecisionNode` → `DiagnosisValidationNode`，不进入 QA `AnswerOutputNode`。
- **适配性**：避免建设第二套 RAG，也避免普通问答的自由文本输出、历史写入和 Web 搜索语义误入诊断。检索后的 `reranked_docs` 成为两个业务的共同证据接口。
- **替代方案与代价**：完全独立的诊断图/检索库隔离更强，但会复制 embedding、索引、召回代码并提高一致性成本；仅用 Prompt 在同一 QA 输出节点上切换行为则无法可靠阻断 Web 和非结构化输出。
- **局限**：共享图意味着任一通用节点的状态或检索回归都会影响两种业务；`diagnosis_placeholder` 仍是异常/无效路径的 fail-closed 降级，维护者须避免误把它当主流程。

### D12. 结构化 `ask` / `answer` / `insufficient`，而不是解析自由文本（重点）

- **当前方案**：`diagnosis_schema.py` 定义 discriminated union；`DiagnosisDecisionNode._invoke_and_parse` 用 JSON 模式 LLM 和 `TypeAdapter` 解析。`ask` 被限制为 1–3 个独立问题、每题 2–4 个选项；页面 `DiagnosisQuestionGroup` 用同轮批量提交。
- **适配性**：问题、选项、引用、终态可持久化、版本化和恢复，前端不需要从自然语言猜测交互结构；资料不足可显式终止而不强行给维修建议。
- **替代方案与代价**：预设故障树确定性更强但不符合当前“基于资料动态追问”的边界；只输出聊天文本实现快，却难以做批量回答、幂等和证据校验。
- **局限**：JSON mode 只提高格式可解析性，不保证事实正确；模型仍可能产生结构合法但不受证据支持的内容，因此后续验证不可省略。

### D13. Prompt 约束之外的可追溯证据和危险操作校验（重点）

- **当前方案**：`services/diagnosis_validation.py:build_trusted_evidence` 仅接受本轮、本地、设备一致、`chunk:<id>` 对得上的 reranked 文档。`validate_diagnosis_candidate` 校验摘录可在原文找到、support text 非通用且与问题/建议对应；对拆机、电气、高温、更换等操作还检查同一证据内的操作与安全条件，以及原文禁止语。
- **适配性**：诊断建议可能涉及安全风险，单靠“不要编造”的 Prompt 不足以提供可审计边界。校验器把来源身份、原文片段和行动建议绑定在程序逻辑中。
- **替代方案与代价**：人工审核、规则故障树或知识图谱可提供更确定安全控制，但人力/建模成本高；只做模型 self-check 易受同一模型幻觉影响。
- **局限**：关键词风险分类与字符串/规范化匹配并非完整安全证明，可能漏检新表述或误拒合理建议；它只能验证“给定检索证据”而不能保证该资料本身完整、最新或适用于用户实体设备。

### D14. 校验失败降级为 `insufficient`，系统失败不伪装为结论（重点）

- **当前方案**：`DiagnosisValidationNode` 将证据/安全拒绝改为受限的 `insufficient`，`diagnosis_status='validation_rejected'`；`DiagnosisService._run_turn` 只允许这种安全降级保存，而 `system_error`、缺候选或被拒绝的维修结论会失败并释放租约。
- **适配性**：诊断语境下“少给建议”优于带错来源或危险建议。会话可明确记录拒绝元数据，而不会把模型候选混成已验证结果。
- **替代方案与代价**：对模型重试更多次可能提高成功率，却增加 LLM 成本和等待；返回未经验证的“低置信建议”体验更完整，却会削弱安全边界。
- **局限**：严格验证会导致更多 `insufficient`。当前 T3 批次未得到用于回归的可信 `answer`；这不否定 T2-07 较早基线的真实 `answer` 验收，两者的基线与回归范围不同。是否因资料、检索、Prompt 或验证规则导致，当前没有统计实验可归因。

### B15. 三轮上限、去重追问与提前结论

`DiagnosisDecisionNode` 和 `DiagnosisSessionRepository.save_question_round` 双重限制最多三轮；前者还规范化问题文本防止重复已答事实。`answer`/`insufficient` 可在任意轮提前产生，`resume_unresolved` 仅允许未满三轮时继续。这是交互时长和安全保守性的产品/实现边界，不表示三轮足以覆盖所有故障。

## 5. 存储、持久化与并发控制

### D16. MongoDB、Milvus、MinIO 职责分离（重点）

- **当前方案**：Milvus 保存文档 chunk 及稠密/稀疏向量，Mongo 保存 `chat_message` 与 `diagnosis_session`，MinIO 保存导入原始文件/图片，并在现有基础设施拓扑中为 Milvus 提供对象存储。入口分别见 `milvus_util.py`、`mongo_history_util.py`、`diagnosis_session_util.py`、`storage_clients.py` 和 `ImportFileService.process_upload_file`。
- **适配性**：把相似度检索、事务式会话记录和二进制对象存储交给各自擅长的系统，避免把历史会话塞进向量库或把原始文件塞进 Mongo。
- **替代方案与代价**：PostgreSQL + pgvector 可减少基础设施种类，但需迁移模型/schema并评估混合检索；只用 Mongo 可简化开发但不等价于当前 Milvus 混合搜索能力；文件落本地盘会影响跨机器复现与备份。
- **局限**：三套存储意味着连接、备份、权限和一致性要分别治理；上传到 MinIO 与后续图入库不是跨存储事务，部分失败需要任务状态和人工排查。

### D17. 诊断把幂等、revision 与 Mongo 租约组合使用（重点）

- **当前方案**：`DiagnosisSessionRepository` 用创建请求唯一索引、`processed_requests`、`revision=expected_revision` 原子条件，以及 `execution` 300 秒租约。`save_answers`、`save_question_round`、`save_final_result` 和反馈都会原子更新并递增 revision。
- **适配性**：动态诊断存在重复点击、网络重传、多个页面和长时间 LLM 推理；单一机制不能同时解决重复写、陈旧写和重复推理。Mongo 单文档原子更新使实现保持在现有基础设施内。
- **替代方案与代价**：Redis 分布式锁/任务队列可处理多实例和长任务，但新增服务/失效语义；数据库事务可扩展多文档一致性，但当前会话操作主要能落在单文档；只靠前端禁用按钮无法抵御重试和多标签页。
- **局限**：租约到期只是可恢复窗口，不等价于任务真正停止；服务多实例、时钟偏差和超长图运行尚未进行压力/故障演练。`resetToStart` 后相同原始描述复用前端 request ID 的交互意图也待确认。

### B18. QA 历史与 Diagnosis 历史的可发现性不同

QA 消息按 `session_id + visitor_id` 存 Mongo，但没有“列出该访客全部 QA 会话”接口；`HistoryPage.tsx` 依赖浏览器 `printcare.qa.session_index` 找会话。Diagnosis 则有 Mongo 访客列表索引和 `/diagnoses`。这是当前功能差异，不宜宣称为统一的跨设备历史系统。

## 6. 异步任务、SSE、恢复与可靠性

### D19. 进程内任务/SSE 与 Mongo 恢复真相源分离（重点）

- **当前方案**：`task_util.py` 维护状态/结果，`sse_util.py` 维护 `queue.Queue`；`sse_generator` 消费事件并移除队列。Diagnosis 另把会话和推理租约写 Mongo，页面在 `DiagnosisPage.recoverAfterStreamIssue` 读取 `/diagnoses/{id}`；QA 则主要读取 `/status/{task_id}` 与 Mongo 消息历史。
- **适配性**：单机受控环境中内存队列实现简洁、延迟低，无需额外消息中间件；诊断把业务状态与传输状态分离，刷新时不必依赖 SSE 重放。
- **替代方案与代价**：Redis Streams、Kafka、持久任务队列或数据库事件表可支持多实例、重放和持久进度，代价是部署、消费位点、清理和幂等逻辑。WebSocket 可双向通信，但用户答题已适合 HTTP，未必降低复杂度。
- **局限**：重启、负载均衡到另一实例或队列提前移除会让 task/SSE 恢复失败；当前没有真实验收活跃流物理断连。QA 失败只写 task error 后关流，Diagnosis 才会显式推 `error` SSE，错误语义尚不统一。

### B20. FastAPI BackgroundTasks 是轻量异步，不是可靠任务平台

路由在返回任务 ID 后用 `BackgroundTasks` 调用同步图；这让浏览器不阻塞，但不提供持久排队、重试调度、并发配额或跨进程可见性。若后续需要高并发导入/长推理，应先评估 Celery/RQ/Arq 或基础设施已有队列，而不是把当前内存 task 表宣传成任务系统。

### B21. 匿名 Cookie 访客隔离是受控演示边界

`query_router.py:_visitor_id` 使用 HttpOnly、SameSite=Lax Cookie 或 header，并在 `/stream`、历史、诊断会话查询中按 `visitor_id` 过滤。它可阻止不同匿名访客直接读取对方已知 ID 的当前接口数据，但不是账户认证、跨设备身份或公网访问控制；Cookie 丢失即丢失访问关联。

## 7. 工程安全、部署、测试与局限

### D22. 管理入口安全默认拒绝，但还不是公网部署设计（重点）

- **当前方案**：`import_router.py:require_admin_access` 校验 `X-PrintCare-Admin-Key` 与 `PRINTCARE_ADMIN_API_KEY`；未配置密钥返回 503，缺失/错误密钥在已配置时返回 401。前端 `AdminPage.tsx` 的输入只保存在内存，上传与状态请求才附带该 header。
- **适配性**：避免导入/知识库管理在受控演示环境匿名开放，同时不把密钥写入 localStorage、代码或请求 URL。
- **替代方案与代价**：OIDC/账号角色、反向代理 Basic/Auth、mTLS 或内网隔离可提供更完整治理，但需要身份、TLS、审计与密钥轮换体系；当前 V1 明确不建设复杂权限系统。
- **局限**：静态 API Key 及 HTTP 开发拓扑不适合公网；没有用户认证、速率限制、审计、HTTPS 终结与密钥轮换。T3 的正确密钥上传仅在临时进程环境变量中验证，不能外推为部署安全完成。

### B23. 分层自动化与受控真实验收要分开解读

后端已有 schema、节点、验证、repository、API 和 Mongo integration 测试（如 `knowledge/test/test_diagnosis_*.py`），前端有会话请求、状态和 SSE 服务测试；`docs/T3-03-06-端到端验收.md` 另记录真实 Mongo/Milvus/LLM/React 联调。前者适合稳定覆盖假来源、风险操作、旧 revision 和重复请求，后者才可说明实际外部依赖联通。固定 K1 评测集、录制/回放模型响应、契约测试和网络故障注入会提升可重复性，但目前尚未建立；历史通过结果也不自动等于每个干净环境可复现。

### B24. 现有 Compose 拓扑可复用，但仅限本地/受控环境

`docs/docker-compose.example.yml` 与 `T4-02-02C` 说明保留 etcd、MinIO、Milvus、Attu、Mongo 的既有版本拓扑；Windows 宿主运行 FastAPI/Vite。示例已脱敏，但不提供公网 TLS、网络隔离、备份恢复、资源限制或生产 secrets 管理，不能称为生产部署方案。

## 10. 需要谨慎表述或不能宣称的能力

- 不能称为“生产级多租户、权限或认证系统”：当前是匿名 Cookie 隔离和单一管理 Key。
- 不能称为“已完成真实故障修复”或“设备安全验证”：没有实体设备闭环，也不是实际售后结论。
- 不能称为“当前版本诊断端到端完全通过”：尽管 T2-07 曾记录真实 `answer → feedback`，当前 T3 的该前端回归及活跃 SSE 物理断连仍是明确未验收项。
- 不能称为“网页/本地资料逐句证明 QA 答案正确”：QA 仅展示进入上下文的来源；只有 Diagnosis 对候选执行严格来源/安全检查。
- 不能将 Compose 示例称为生产部署或干净环境完全复现：T4-02 已记录依赖、初始化和验证缺口。
- 不能声称 RRF、HyDE、Rerank 或任一参数“提升了多少”：仓库没有可引用的离线评测和性能数据。

## 11. 适合后续单独学习的基础知识

- Milvus 混合检索：稠密/稀疏向量、`WeightedRanker`、过滤表达式与 RRF 的适用边界。
- RAG 评测：召回率、重排指标、答案基准集、成本/延迟测量，以及如何比较 HyDE 与 query expansion。
- LangGraph 并行 state 合并：增量更新、条件边、失败传播和共享图的回归测试。
- 结构化 LLM 输出：JSON schema/Pydantic、有限重试、模型输出与程序验证的职责划分。
- Mongo 单文档并发控制：乐观锁、条件更新、幂等键、租约/过期恢复和多实例语义。
- SSE/EventSource：代理、断线、超时、重连、事件重放与持久队列的差异。
- 安全工程：最小权限、API Key 生命周期、威胁建模、危险操作的证据约束与部署层防护。
