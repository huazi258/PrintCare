# T4-02-01 本地运行说明

本文依据当前代码与 `docs/T4-01-01-仓库现状盘点.md` 整理，面向本地/受控演示。未在本任务中安装依赖、启动服务或调用真实 LLM；命令是代码入口和既有 T3 验收命令的汇总，不构成干净机器已验证的复现承诺。

## 1. 运行形态与前置条件

当前系统需要三个本地进程：查询服务（8001）、导入服务（8000）和 Vite 前端（示例为 5174）。前端开发代理由 `frontend/vite.config.ts` 将 `/api/core` 转发到 8001、`/api/admin` 转发到 8000。

| 项目 | 当前依据 | 前置条件 |
| --- | --- | --- |
| Python | 本机历史环境为 Python 3.10；后端入口和依赖位于 `knowledge/`。 | 建议使用 Python 3.10。仓库没有 Python 版本锁定或完整可验证的依赖锁。 |
| Node.js | `frontend/package.json` 要求 Node `>=22`，并提供 `package-lock.json`。 | 安装 Node 22 或更高版本与 npm。 |
| LLM、BGE-M3、Reranker | `knowledge/utils/client/ai_clients.py` 读取兼容 OpenAI 的接口和本地模型路径。 | 具备合法 API 凭据、可访问的 API 地址，以及存在的 BGE-M3/Reranker 本地模型目录；GPU、CUDA 与 fp16 是否可用取决于本机。 |
| MongoDB | `StorageClients.get_mongo_db()` 用于问答历史与诊断会话。 | 可连接的 MongoDB，且账户有目标数据库读写权限。 |
| Milvus | 查询和导入均通过 `MilvusClient` 访问。 | 可连接的 Milvus，且允许创建/读取 Collection 与索引。 |
| MinIO | 导入服务先保存原文件到 MinIO。 | 可连接的 MinIO；当前客户端以 HTTP（`secure=False`）连接，配置值不含协议。 |
| MinerU/PyTorch | PDF 导入依赖 `mineru[pipeline]`、`pdftext` 和 PyTorch。 | 按平台准备兼容的 PyTorch/MinerU 组合；仓库未提供已验证的干净环境安装方案。 |

不接入实体打印机，也不应把软件连通性当作真实维修验证。

## 2. 安全配置

将 `knowledge/.env.example` 复制为本机忽略的 `knowledge/.env`，再替换占位符。若 `knowledge/.env` 已存在，**不要执行会覆盖它的复制命令**，仅人工对照补齐缺失键。

```powershell
Set-Location G:\codex-work\PrintCare\knowledge
Copy-Item .env.example .env
```

`knowledge/.env.example` 已按实际读取路径分组：

| 分类 | 必需性 | 变量 |
| --- | --- | --- |
| LLM 与本地模型 | 查询、诊断和导入所需 | `DASHSCOPE_API_KEY`、`OPENAI_API_BASE`、`LLM_DEFAULT_MODEL`、`BGE_M3_PATH`、`BGE_RERANKER_LARGE`、`BGE_DEVICE`、`BGE_FP16` |
| MongoDB、Milvus | 查询/诊断所需；Milvus 也用于导入 | `MONGO_URL`、`MONGO_DB_NAME`、`MILVUS_URL` |
| MinIO | 通过导入服务上传时所需 | `MINIO_ENDPOINT`、`MINIO_ACCESS_KEY`、`MINIO_SECRET_KEY`、`MINIO_BUCKET_NAME` |
| K1 Collection | 查询和导入必须指向同一组 | `CHUNKS_COLLECTION`、`ITEM_NAME_COLLECTION`；`ENTITY_NAME_COLLECTION` 目前仅被配置类读取，未发现活跃查询/导入调用。 |
| QA Web MCP | 仅普通 `qa` 模式联网分支需要 | `MCP_DASHSCOPE_BASE_URL`、`OPENAI_API_KEY`。诊断模式由图路由禁止调度 Web MCP。 |
| 管理接口 | 上传或查询导入任务时所需 | `PRINTCARE_ADMIN_API_KEY`，通过请求头 `X-PrintCare-Admin-Key` 发送，绝不能放入 `VITE_*`。 |
| 兼容/可选调优 | 不设置时采用代码默认值，或当前未发现活跃调用 | `MODEL`、`ITEM_MODEL`、`VL_MODEL`（图片处理路径）、`EMBEDDING_DIM` 及 `.env.example` 中注释列出的检索阈值。 |

前端仅使用 `frontend/.env.example` 中的 `VITE_CORE_API_TARGET` 与 `VITE_ADMIN_API_TARGET`；它们的默认值分别是 `http://127.0.0.1:8001`、`http://127.0.0.1:8000`。前端环境文件不得包含任何 API Key、数据库或 MinIO 凭据。

## 3. 基础设施与 K1 数据

1. 启动并确认 MongoDB、Milvus、MinIO 可从本机访问；仓库没有 Compose、Dockerfile 或健康检查脚本。
2. 设置与 `docs/04-T1环境配置说明.md` 一致的 `CHUNKS_COLLECTION=printcare_k1_chunks_v1`、`ITEM_NAME_COLLECTION=printcare_k1_item_names_v1`，并与旧课程 Collection 隔离。
3. Collection 可由导入图中的 `knowledge/processor/import_process/nodes/import_milvus.py` 在导入时按实际向量维度创建 Schema/索引；仓库没有独立、可重复执行的初始化或迁移脚本。不要为此目的手动删除或重建已有 Collection。
4. 准备有权使用的 K1 PDF 或 Markdown。导入入口最终只接受 `.pdf`、`.md`（由 `nodes/entry.py` 判断）；路由层尚无文件大小限制，受控环境应自行约束上传来源和体积。

## 4. 安装依赖（尚未在干净环境验证）

前端依赖具有 lockfile，可在 `frontend/` 使用：

```powershell
Set-Location G:\codex-work\PrintCare\frontend
npm ci
```

后端只有 `knowledge/requirements.txt`，可用下列命令建立尝试环境：

```powershell
Set-Location G:\codex-work\PrintCare\knowledge
py -3.10 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

这不是已验证的从零安装流程。`requirements.txt` 对 PyTorch/CUDA 的注释要求先安装 requirements、再单独处理 PyTorch；实际模型、显卡和 MinerU 版本组合需要另行验证。

### 已记录的依赖缺口（本轮不修复）

- 后端直接导入但未在 `requirements.txt` 显式列出的顶层包：`fastapi`、`uvicorn`、`python-dotenv`、上传表单所需的 `python-multipart`；`FlagEmbedding` 也被直接导入，不能假定 `pymilvus[model]` 在所有版本都会提供它。
- `openai`、`langchain-core`、`starlette` 等可能来自传递依赖，当前没有直接版本约束；`openai-agents` 已列出但未锁定版本。
- 大多数 Python 依赖没有锁定版本，且仓库没有 Python 版本文件；Windows、CPU/GPU、CUDA 12.8、PyTorch 与 MinerU 的兼容性都未形成验证矩阵。

## 5. 启动与停止

以下命令应从仓库根目录分别在三个 PowerShell 窗口运行。端口来自 `knowledge/api/query_router.py`、`knowledge/api/import_router.py` 和 T3 的实际验收记录。

```powershell
# 窗口 1：查询服务
Set-Location G:\codex-work\PrintCare
.\knowledge\.venv\Scripts\python.exe -m uvicorn knowledge.api.query_router:create_app --host 127.0.0.1 --port 8001
```

```powershell
# 窗口 2：导入服务
Set-Location G:\codex-work\PrintCare
.\knowledge\.venv\Scripts\python.exe -m uvicorn knowledge.api.import_router:create_app --host 127.0.0.1 --port 8000
```

```powershell
# 窗口 3：前端开发服务器
Set-Location G:\codex-work\PrintCare\frontend
npm run dev -- --host 127.0.0.1 --port 5174
```

在每个窗口按 `Ctrl+C` 停止对应进程。没有统一的停止脚本；不要用结束数据库容器/删除卷来代替正常停止。

## 6. 健康检查与最小验证

不调用模型的服务检查可在服务启动后执行：

```powershell
Invoke-RestMethod http://127.0.0.1:8001/openapi.json
Invoke-RestMethod http://127.0.0.1:8000/openapi.json
```

前端启动后，在浏览器访问 `http://127.0.0.1:5174/`；也可访问 `http://127.0.0.1:5174/api/core/openapi.json`、`http://127.0.0.1:5174/api/admin/openapi.json` 核对 Vite 代理。上述检查只证明进程/代理可达，不证明模型、数据库或业务流程可用。

具备受控基础设施、合法凭据和 K1 资料后，最小业务验证顺序是：在管理页以管理员密钥上传自有 `.md`/`.pdf` 并等待任务状态完成，再从 QA 页面执行一条 K1 问答，最后检查来源是否来自实际命中的本地资料或明确标记的网页来源。诊断还应单独确认不触发 Web MCP。真实诊断 `answer → feedback` 和活跃 SSE 物理断连恢复仍未完成端到端验收，不能把此顺序的局部成功写为 T3 完整通过。

## 7. 常见问题与已知复现缺口

| 现象 | 先核对的依据/限制 |
| --- | --- |
| 服务启动即提示缺少环境变量 | 对照 `knowledge/.env.example`；注意 LLM 客户端实际要求 `DASHSCOPE_API_KEY` 与 `LLM_DEFAULT_MODEL`，Web MCP 另用 `OPENAI_API_KEY`。 |
| 导入服务返回 401 或 503 | `/upload`、`/status/{task_id}` 必须携带 `X-PrintCare-Admin-Key`；未配置 `PRINTCARE_ADMIN_API_KEY` 时服务端安全地返回 503。 |
| 查询无 K1 结果或混入旧资料 | 确认两项 K1 Collection 名称、文档的 `device_id=creality-k1` 归属，以及没有指向旧课程 Collection。 |
| MinIO 地址无效 | `MINIO_ENDPOINT` 传给 MinIO 客户端时应为 `host:port`，不是含协议的 URL；当前实现固定 `secure=False`。 |
| PDF/模型安装失败 | 当前依赖和 GPU/CUDA 组合未锁定；不要将一次安装成功推广为跨机器可复现结论。 |
| 前端请求失败 | 核对 Vite 的两个 `VITE_*_API_TARGET` 与 8000/8001 进程；生产反向代理/静态托管尚未定义。 |

干净机器仍不能可靠复现：缺少完整 Python 依赖锁、外部基础设施 bootstrap/Compose、模型获取与平台兼容说明、可再分发 K1 种子资料和独立 Collection 初始化脚本。后续修复这些缺口前，应继续区分“已有本机环境可运行”和“干净环境可复现”。
