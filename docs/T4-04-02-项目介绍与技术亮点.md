# T4-04-02 项目介绍与技术亮点

> 整理日期：2026-10-13。本文面向项目介绍、简历和面试准备，依据当前源码、Git 提交历史、T4-03 技术文档及 T2/T3 验收记录提炼；不替代完整架构文档，也不主张未经验证的性能或生产能力。

## 1. 项目介绍

### 一句话版本

PrintCare AI 是面向 Creality K1 的 AI 技术支持平台：将设备资料转化为带来源的知识问答，并用受本地证据约束的多轮诊断协助用户排查故障。

### 简历版本（约 130 字）

PrintCare AI 是基于课程项目既有 RAG 与导入能力进行二次开发的 3D 打印技术支持平台，当前聚焦 Creality K1。项目以 React、FastAPI、LangGraph 和 Milvus 构建知识问答与动态诊断：QA 通过混合检索、HyDE、RRF 与重排序生成带来源的流式回答；诊断复用检索链路，但由服务端设备过滤、结构化决策和证据/安全校验约束输出。MongoDB 以幂等键、revision 与推理租约维护多轮会话一致性。

### 面试口述版本（约 1 分钟）

这个项目解决的是桌面级 3D 打印用户遇到问题时，资料分散、故障描述又不够精确的问题。它当前只支持 Creality K1，并把流程分成明确的知识问答和智能诊断两条路径。问答侧沿用一套 RAG：本地资料经过稠密/稀疏混合检索、HyDE 扩展、RRF 融合和重排序后，由模型流式生成答案，并把真正进入上下文的来源展示出来。诊断侧不让模型直接自由回答，而是复用同一检索图后，让模型生成结构化追问或结论，再由程序校验设备归属、引用证据和操作安全；资料不够就保守返回 `insufficient`。工程上，诊断会话用 MongoDB 保存，结合 `request_id`、revision 和租约处理重复提交、旧页面写入和并发推理，SSE 只负责当前进程的实时反馈。项目已有真实 K1 QA、诊断追问、上传和并发控制的受控环境验证，但不能表述为生产级系统或完整诊断端到端验收已通过。

## 3. AI 应用 / Agent 工程方向简历候选

### 项目简介

PrintCare AI：面向 Creality K1 的 RAG 技术支持与动态故障诊断应用。项目在既有课程 RAG 基础上，采用 LangGraph 编排检索、生成与校验节点，为 QA 和证据约束诊断提供不同的受控执行路径。

### 技术描述候选

- 以 LangGraph 编排直接检索、HyDE 检索、RRF 融合、Rerank 与输出节点；通过显式 `mode` 复用检索能力，并在诊断路径程序化阻断 Web MCP。
- 设计结构化诊断结果 `ask` / `answer` / `insufficient`，在模型生成后执行本地证据、设备归属、重复追问和高风险建议校验，证据不足时安全降级。
- 实现 K1 设备归属的服务端检索过滤与 QA 本地/网页来源标注，避免将网页结果伪装为设备手册，并让页面展示实际进入生成上下文的来源。
- 基于 MongoDB 的 `request_id`、revision 条件更新和推理租约实现多轮诊断会话一致性；受控环境已验证旧 revision 409 与重复请求幂等。

### 使用提示

若投递材料要求第一人称贡献，须由负责人确认本人实际负责的节点、接口、测试或联调范围后，再将“项目实现”替换为“负责/主导”。不要把 LangGraph 工作流泛化为多 Agent 系统，也不要声称模型经过微调或取得量化检索提升。

## 4. AI 全栈开发方向简历候选

### 项目简介

PrintCare AI：以 React + FastAPI 构建的 K1 技术支持 Web 应用，提供知识问答、动态诊断、历史记录和受控知识库导入；查询、导入与基础设施职责保持分离。

### 技术描述候选

- 使用 React、TypeScript、Vite 构建工作台、QA、诊断、历史和知识库管理页面，集中封装 HTTP/SSE 通信、任务状态及诊断恢复界面。
- 维护 FastAPI 查询服务（8001）与导入服务（8000），通过开发代理统一浏览器入口；以 Pydantic 契约承接 QA、诊断、反馈和导入状态接口。
- 将 MongoDB 用于问答历史与诊断会话，Milvus 用于 K1 向量/稀疏索引，MinIO 用于原始文档对象；明确 SSE 传输与持久化状态的职责边界。
- 完成受控环境下 QA 流式输出与来源、History、Admin 鉴权上传、revision 冲突和请求幂等的联调记录；前端 lint/test/build 与后端单测均有已记录回归结果。

### 使用提示

不要把开发代理或当前 Linux VM Compose 示例描述为生产部署。对“完成联调”“完成测试”等措辞，应限定在验收报告所记录的范围，不推及未复验的诊断 `answer → feedback` 和活跃 SSE 物理断连。

## 5. 面试讲解素材

### 1 分钟项目介绍

可以使用第 1 节的面试口述版本。答题时建议先说业务问题和两条入口，再用“检索约束—结构化诊断—会话一致性”三点说明工程实现，最后主动说明 K1 单设备、受控环境和当前验收边界。

### 3 分钟技术讲解提纲

1. **问题与边界（约 30 秒）**：K1 用户资料分散、描述不完整；项目不控制实体设备，诊断只能基于已导入的可信 K1 本地资料。
2. **整体路径（约 35 秒）**：React 经两个 FastAPI 服务进入 LangGraph；Milvus 负责检索，MongoDB 保存历史/会话，MinIO 保存导入对象，SSE 负责当前请求的实时输出。
3. **QA 检索设计（约 40 秒）**：稠密/稀疏混合检索与 HyDE 并行，RRF 合并本地候选，Rerank 再统一比较本地与 QA 网页结果；来源只记录实际进 Prompt 的文档。
4. **诊断安全设计（约 50 秒）**：显式 mode 阻断 Web MCP；LLM 生成结构化候选，验证器检查证据、设备和安全性；不确定时返回 `insufficient`，而不是凭常识给高风险操作。
5. **可靠性与验证（约 25 秒）**：`request_id`、revision、租约处理重试和并发；真实验收覆盖 QA、动态追问、Admin 上传、409 和幂等，同时说明当前 answer 反馈回归与真实 SSE 断连尚未完成。

### 重点追问及回答要点

| 追问 | 回答要点 |
| --- | --- |
| 为什么不用一套自由问答同时处理诊断？ | 诊断需要可审计的本地证据、设备隔离和安全限制。共用检索结果，但在 Rerank 后用独立决策/验证节点，避免 QA 的网页搜索和自由文本语义进入诊断。 |
| K1 约束如何真正生效？ | 服务端将设备规范化，并把 `device_id` 与名称过滤下推到 Milvus 召回前；不是只在 Prompt 中要求模型忽略其他设备。 |
| 混合检索的具体链路是什么？ | 直接查询和 HyDE 各自生成 BGE-M3 稠密/稀疏向量进行混合检索，RRF 合并本地候选，随后再与 QA 网页候选一起 Rerank。 |
| 为什么网页搜索不参与诊断？ | 网页内容不能满足“已导入、归属当前设备的可信本地资料”边界；代码在 Web MCP 节点创建客户端前检查 `mode` 并返回。 |
| 如何避免模型编造维修建议？ | 模型输出结构化候选；验证器回查本轮实际命中的本地片段、设备归属与支持文本，并拦截高风险建议。无法通过则有限重试或降级为 `insufficient`。 |
| 多轮会话如何避免重复推进？ | `request_id` 处理同操作重试，revision 条件更新拒绝旧页面提交，租约避免两个任务同时推理同一会话；结果和轮次写入 MongoDB。 |
| 为什么仍要 MongoDB，不能只靠 LangGraph State？ | Graph State 只属于一次执行；刷新、重启、反馈和历史查询都需要持久化会话，进程内任务表/SSE 队列不能作为真相源。 |
| SSE 断线如何处理？ | 当前实现可处理不存在任务、网络错误和 30 秒无事件超时，并回退读取持久化状态；活跃流物理断连尚未真实复验，不能声称可靠重放。 |
| 已有哪些真实验证？ | T3 记录了真实 K1 QA SSE/来源、诊断动态 ask、Admin 授权上传、真实 409 和幂等；T2 历史基线记录过 answer/反馈。当前 T3 没有新的 answer 前端回归样本。 |
| 课程代码与新增内容如何区分？ | Git 记录显示查询/导入根目录早于 K1 约束、诊断会话/校验、React 前端和结构化来源等后续提交；只能据此说明演进顺序，个人贡献仍需负责人确认。 |
