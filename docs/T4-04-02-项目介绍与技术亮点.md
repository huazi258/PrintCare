# T4-04-02 项目介绍与技术亮点

> 整理日期：2026-10-14。本文服务于简历、GitHub 展示和技术面试，依据当前源码、Git 历史、README、T4-03 技术文档及 T2/T3 验收资料编写。这里的“独立主导”采用项目负责人对个人职责的说明；客观实现与验证范围仍以源码和验收记录为准。

## 1. 项目定位与个人贡献

PrintCare AI 是一个面向 Creality K1 的个人 AI 全栈技术支持项目：把受控设备资料转化为带来源的知识问答，并以本地证据约束的动态诊断辅助用户排查故障。

项目负责人独立主导产品需求规划、技术方案设计、RAG 架构设计、动态诊断方案、前后端开发组织、联调及验收。其中，RAG 的设计与落地包括：面向 K1 的知识范围约束、BGE-M3 稠密/稀疏混合检索、HyDE、RRF、Rerank，以及 QA/Diagnosis 的双模式工作流和来源管理机制。

项目具有公开课程工程基础；上述表述强调在 PrintCare 中完成的方案设计、架构组织和工程实现责任，不表示自研 Embedding、Reranker、LangGraph、Milvus 或底层检索算法。对外材料无需展开课程背景，但不得声称从零编写了全部基础代码。

## 2. 项目介绍（三种版本）

### 一句话版本

独立设计并实现面向 Creality K1 的 RAG 技术支持平台，以混合检索和 LangGraph 双模式工作流提供带来源的知识问答与受证据约束的动态故障诊断。

### 简历版本（约 150 字）

独立主导 PrintCare AI 的产品与技术方案，构建面向 Creality K1 的 AI 全栈技术支持平台。设计基于 BGE-M3 的稠密/稀疏混合检索，结合 HyDE、RRF 和 Rerank 完成多阶段 RAG 问答与来源管理；使用 LangGraph 设计 QA/Diagnosis 双模式工作流，诊断通过本地证据、设备归属和安全校验生成结构化追问或保守结论。基于 React + FastAPI 实现业务界面与 API，以 MongoDB 的幂等键、revision 和推理租约维护多轮会话一致性。

### 面试口述版本（约 1 分钟）

PrintCare AI 是我独立主导的个人 AI 全栈项目，目标是解决 K1 用户排障时资料分散、描述不精确的问题。我先把场景拆成知识问答和智能诊断两条路径：问答侧设计了一套多阶段 RAG，使用 BGE-M3 稠密/稀疏混合检索，结合 HyDE 扩展查询、RRF 融合和 Rerank 选取上下文，再流式输出带来源的答案。诊断侧复用检索能力，但我在 LangGraph 中用显式 mode 把它与 QA 分流：诊断禁止 Web MCP，只能使用当前 K1 的本地证据。模型只生成结构化的追问或候选结论，服务端再校验证据、设备归属和危险操作，资料不足时返回 `insufficient`。工程上，我用 React + FastAPI 完成页面和接口，用 MongoDB 的 `request_id`、revision 和推理租约保证多轮会话不会因重复点击或旧页面写入而错乱，SSE 负责实时展示。当前已有真实 K1 QA、动态追问、上传、409 冲突和幂等验证；但不把它包装成生产系统，也不宣称当前诊断 answer 反馈闭环已经完整复验。

## 4. AI 应用 / Agent 工程简历版本

**PrintCare AI｜个人项目｜Python、FastAPI、LangGraph、Milvus、MongoDB、BGE-M3、React**

独立设计并实现面向 Creality K1 的 RAG 技术支持与动态故障诊断应用，围绕“可信本地资料约束下的检索、决策和会话可靠性”构建 QA 与 Diagnosis 双模式工作流。

- 独立设计 BGE-M3 稠密/稀疏混合检索链路，结合 HyDE、RRF 与 Rerank 构建多阶段 RAG；将网页结果保留在本地 RRF 之外，并在统一重排序后标明来源类型。
- 基于 LangGraph 设计 QA/Diagnosis 显式分流，复用检索和 `reranked_docs`；在诊断路径程序化隔离 Web MCP，避免外部网页证据进入设备诊断。
- 设计动态诊断结构化契约与验证器：LLM 输出 `ask` / `answer` / `insufficient` 后，校验证据引用、K1 归属、重复追问和高风险建议，失败时安全降级。
- 设计 MongoDB 会话状态模型，以 `request_id`、revision 条件更新与推理租约处理幂等、旧页面冲突和并发推理；真实受控验证覆盖 409 冲突与重复请求幂等。

**表述边界**：可称为 LangGraph 工作流/AI 应用工程，不称为多 Agent 系统；不声称自研模型、微调模型、检索算法原创或量化效果提升。

## 5. AI 全栈开发简历版本

**PrintCare AI｜个人项目｜React、TypeScript、Vite、FastAPI、LangGraph、MongoDB、Milvus、MinIO**

独立主导面向 Creality K1 的 AI 技术支持 Web 应用，完成知识问答、动态诊断、历史记录和受控知识导入的全栈业务闭环，并将模型流程、持久化状态与实时交互分层组织。

- 独立构建 React 五页面应用，集中封装 HTTP/SSE 通信、任务状态、结构化来源展示和诊断恢复界面；通过 Vite 代理连接查询服务与导入服务。
- 设计 FastAPI 查询/导入 API 边界与 Pydantic 契约，集成 LangGraph、管理端 Key 校验及受控 PDF/Markdown 导入流程。
- 设计 MongoDB（问答历史、诊断会话）、Milvus（K1 稠密/稀疏向量索引）和 MinIO（原始文件对象）的职责分工，避免将 SSE 进程内队列当作持久化状态。
- 完成受控环境下 QA 流式回答与来源、History、Admin 鉴权上传、旧 revision 409 和请求幂等的真实联调；已有前端 lint/test/build 与后端单测回归记录。

**表述边界**：不把开发代理、Linux VM Compose 示例或匿名 Cookie 隔离描述为生产部署、完整权限体系或多租户系统。

## 6. 面试介绍与技术追问

### 1 分钟介绍

优先使用第 2 节的面试口述版本。建议按“业务问题 → RAG 设计 → 诊断约束 → 状态可靠性 → 验证边界”顺序讲述，既体现独立方案设计，也能主动界定未验证范围。

### 3 分钟核心技术讲解提纲

1. **问题与目标（30 秒）**：K1 用户资料分散、故障描述不完整；我将产品拆为来源可见的 QA 和以本地资料为边界的动态诊断。
2. **RAG 设计（45 秒）**：直接查询与 HyDE 并行生成 BGE-M3 稠密/稀疏检索请求，RRF 合并本地候选；Rerank 再比较本地和 QA 网页候选，来源只记录真正进入 Prompt 的资料。
3. **双模式工作流（40 秒）**：LangGraph 复用检索链，但以 `mode` 在 Rerank 后分流。QA 可以使用 Web MCP；Diagnosis 在代码路径上禁止联网，并以 K1 服务端过滤保证证据范围。
4. **动态诊断与安全（45 秒）**：模型只返回结构化候选，验证器检查每轮问题、引用和危险操作；资料不足或校验失败时返回 `insufficient`，避免把模型常识包装为维修建议。
5. **全栈可靠性与验证（20 秒）**：React + FastAPI 通过 SSE 呈现实时过程；MongoDB 保存会话，`request_id`、revision、租约解决重试和并发。最后如实说明已验证的受控链路与尚未完整复验的路径。

### 重要追问及回答思路

| 追问 | 回答要点 |
| --- | --- |
| 为什么为 RAG 同时使用稠密和稀疏检索？ | K1 资料既有精确型号、参数和错误术语，也有自然语言操作描述。两类信号互补，但项目没有把它包装成已量化优于单路检索。 |
| HyDE 在这里解决什么问题？ | 用户的故障描述可能口语化；HyDE 生成可能的技术文档表述，作为第二条检索视角，再由 RRF 合并，不直接把假设文本当作答案。 |
| 为什么选择 RRF，而不直接混合两路分数？ | 直接检索和 HyDE 分支的分数不一定同尺度；RRF 基于排名融合，更适合作为当前两路本地候选的轻量合并策略。 |
| Rerank 与 Milvus 混合检索分别做什么？ | Milvus 负责先以稠密/稀疏信号高效召回；Reranker 以完整问题统一比较候选，且可把结构不同的网页候选与本地候选放到同一选择阶段。 |
| K1 约束如何真正生效？ | 服务端规范化设备，并把 `device_id` 与名称过滤下推到 Milvus 召回前；不是仅要求模型忽略其他型号。 |
| 为什么 QA 和 Diagnosis 共用图却不能共用输出？ | 共用检索可避免维护两套 RAG；但诊断需要本地证据、安全校验与结构化状态，所以在 Rerank 后进入独立决策/验证节点，不走 QA 自由文本输出。 |
| 如何防止模型给出无依据或危险建议？ | 验证器回查本轮命中的本地资料、引用片段和支持文本，并拒绝错误设备、重复问题和高风险操作；不通过则有限重试或安全降级。 |
| 幂等、revision、租约分别解决什么？ | `request_id` 抵御同一操作重试；revision 拒绝旧页面覆盖新状态；租约避免两个后台推理同时推进一个诊断会话。 |
| SSE 断线为什么不能只靠重连解决？ | 进程内队列不保证重启后事件重放，所以刷新/恢复要读取 MongoDB 持久化会话。当前网络错误和超时有处理，但活跃流物理断连尚未真实复验。 |
| 哪些验证可以如实说，哪些不能？ | 可说真实 K1 QA SSE/来源、动态 ask、Admin 上传、409 与幂等受控验证；T2 历史基线有 answer/反馈，当前 T3 没有新的该回归样本，不能说当前版本完整诊断端到端通过。 |
