# PrintCare AI 技术架构与改造方案

> 版本：V0.1（技术设计评审稿）  
> 日期：2026-10-09  
> 状态：**仅用于设计与评审，不代表已实现；本阶段禁止直接据此开始大规模重构**  
> 关联文件：`01-产品需求文档.md`、`01A-产品决策记录.md`  
> 代码依据：[`huazi258/PrintCare`](https://github.com/huazi258/PrintCare) 当前 `main` 分支的静态检查，以及 Codex 第一阶段技术报告。未执行本地服务、数据库或端到端测试。

## 0. 总体结论与设计原则

**一句话方案：保留原项目的文档导入与完整 RAG 检索管线，新增基于现有检索结果的动态诊断分支；用 React + Vite 重做用户界面，不大规模重写 FastAPI。**

- **保持核心**：PDF/Markdown 解析、图片处理、切分、BGE-M3、Milvus、向量/HyDE 检索、RRF、Rerank、普通问答的 SSE 输出。
- **按需扩展**：设备明确归属、诊断上下文整合、LLM 结构化诊断、MongoDB 诊断状态、来源校验、诊断 UI。
- **不引入**：新向量数据库、第二套 RAG、预设故障树、多 Agent、微调、独立任务队列平台、全面服务合并、生产级账户系统。
- **开发顺序**：先保证旧问答不回归，再接入动态诊断，最后替换前端。每一步保留可回退的基线。

### 0.1 少量必要概念

- **RAG 检索管线（Pipeline）**：把提问变成检索请求，从知识库找证据，经过融合与重排序后交给模型。两种业务模式可共用这段流程。
- **LangGraph State（图状态）**：某次工作流运行中，各节点传递的数据；不是自动持久化的用户历史。
- **诊断会话（diagnosis session）**：跨多次用户提交持续存在的一次故障排查记录，需保存在 MongoDB。
- **SSE**：服务端向浏览器单向发送实时事件；选项答案仍由浏览器通过 HTTP POST 提交。
- **结构化输出**：模型按约定返回可验证的字段（例如 `ask`、问题数组、引用 ID），而不是让前端解析随意生成的自然语言。

## 2. 现有架构（As-Is，静态代码已核对）

### 2.1 文档导入

```text
POST /upload (FastAPI :8000)
  → ImportFileService
  → LangGraph 导入图
  → 类型判断 → PDF 转 Markdown / Markdown 直接进入
  → 图片处理 → 文档切分 → 商品名识别
  → BGE-M3 向量化 → Milvus 入库
  → 文件上传至 MinIO，任务状态供 /status/{task_id} 查询
```

代码入口：`knowledge/api/import_router.py`、`knowledge/services/import_file_service.py`、`knowledge/processor/import_process/main_graph.py`。

### 2.2 查询问答

```text
POST /query (FastAPI :8001)
  → QueryService
  → item_name_confirm
  → [vector_search | hyde_search | web_search_mcp] 并行
  → RRF → Rerank → answer_output
  → MongoDB 保存聊天消息；SSE progress/delta/final
```

代码入口：`knowledge/api/query_router.py`、`knowledge/services/query_service.py`、`knowledge/processor/query_process/main_graph.py`。

`rerank` 节点已在状态中提供 `reranked_docs`，文档结构大致为 `content`、`title`、`chunk_id`、`url`、`source`、`score`。这是**诊断最重要的复用入口**。现有 `answer_output` 同时负责构建 Prompt、LLM 生成、历史写入与 SSE 推送，不应无条件作为诊断分支的出口。

### 2.3 当前限制（不是新增功能）

- 查询服务缺失前端会调用的 `/status/{task_id}`；历史清理前端发 DELETE，但路由定义重复使用 GET。
- `get_recent_messages()` 倒序返回，不适合作为按时间理解的诊断上下文；型号历史回填函数仍有 TODO。
- 查询任务和 SSE 队列存在进程内存中，不能作为跨刷新和重启的诊断状态来源。
- 商品识别目前以 `item_name` 为核心，导入的设备归属依赖模型识别；新的 K1 资料不应继续只靠猜测归属。
- 原前端为 `knowledge/front/chat.html`、`import.html`，上传页 API 地址硬编码；现有 Web 引用信息不够适合产品级“查看依据”。
- 以上均属静态发现；现有系统已可在用户本机运行，但回归表现需在开发阶段重新测试。

### 4.1 设备型号归属：显式指定优先

建议在数据中同时保留：

- 设备稳定标识 `device_id`：例如 `creality-k1`（以后可加 K1 Max）。
- 显示名 `device_model`：例如 `Creality K1`。
- 向后兼容 `item_name`：检索阶段暂时把已确认的规范型号写入现有 `item_names=[...]`，延续 Milvus 原有过滤，不立即更改整库 Schema。

管理员上传时选择设备（V1 默认 K1），数据归属来自**管理员输入和服务端校验**，而不是仅依赖 LLM 从手册中识别。旧导入节点可以在明确设备时绕过/覆盖商品名抽取结果，精确修改点需在开发时测试。

注意：既有非 K1 测试资料与新设备资料应隔离。若 V1 采用新的干净演示库，可以重新导入合法使用的 K1 资料，避免为旧测试数据编写复杂迁移脚本。不能把检索时字符串匹配视为充分隔离，必须通过验证集检查。

### 4.2 检索来源与引用

对 `reranked_docs` 做薄层标准化：`source_id`（可信引用键）、`source_type`（local/web）、`device_id`（本地资料）、`file_title`、`title`、`chunk_id`、`url`（若有）、`content` 或摘录。仅返回实际有的数据，不伪造页码和定位。

- 普通问答：允许本地与 Web；来源在 UI 上明显区分。
- 诊断：**只接受本地 K1 来源**；模型返回的每个引用 ID 由服务端与本轮检索命中集合核对，不合法则剔除或拒绝该诊断建议。
- 检索不到可靠资料：返回 `insufficient`，不能悄悄回退到模型常识生成维修指令。
- 原 `answer_output` 的来源格式化存在集合解包顺序问题，列入回归修复项；是否需要补充文档来源字段以实际数据为准。

## 5. 动态交互式诊断设计

### 5.1 不新增第二套 RAG

诊断仅增加**上下文装配、诊断决策、结果输出**三个逻辑职责；可以在原查询图上添加少量节点/条件边，不强制拆出独立检索服务。

```text
[服务层] 读取 MongoDB 诊断会话 + 整合原始故障、已答问题、已确认事实
      → 生成完整 rewritten_query（不能仅用“首层就脱落”等孤立选项）
      → [共享查询图] 已选 K1 校验 → 本地 Vector + HyDE → RRF → Rerank
      → diagnosis_decision（模型结构化判断）
      → diagnosis_output（持久化后发送 SSE 结构化诊断事件）
      → END
```

普通 `qa` 仍按原流程运行并可调用 Web MCP。两种模式不自动相互切换。

**注意图中的提前结束路径**：原 `item_name_confirm` 在无法确认商品时可能直接跳转 `answer_output`。诊断模式需要改为结构化的设备确认/资料不足响应，不能错误进入普通回答节点。

### 5.2 诊断输出约定（概念契约，不是最终代码）

决策动作只有三种：

| `action` | 模型应返回 | 服务端/前端做什么 |
| --- | --- | --- |
| `ask` | 1～3 个相互独立的问题，单题 2～4 个选项、问题标识、引用 | 验证格式与依据；保存后渲染选项卡片，等待批量提交 |
| `answer` | 结论边界、排查步骤、所依赖的引用键、安全提示 | 验证引用；展示建议，等待用户反馈结果 |
| `insufficient` | 资料不足的原因、目前已确认事实、可转向的官方支持渠道（若有） | 标明不确定并终止自动追问 |

用户每轮可对多题统一提交；支持“不确定”和必要的补充文字。**问题由模型结合本地文档动态生成，不建设人工故障树。**

结构化对象由 Pydantic 校验。重要约束不能仅写在 Prompt 中：

1. 每轮问题数量 ≤ 3，澄清轮次 ≤ 3，达到上限后禁止再返回 `ask`。
2. 新问题不得与已确认问题语义重复；遇到模型重复或格式不合法，有限重试后安全回退。
3. `answer` 的操作步骤必须有与当前型号匹配的本地引用；涉及高温、电气、拆机等危险步骤时保守处理。
4. 所有引用只能指向本轮实际命中的来源；不允许用户提交伪造的引用对象覆盖检索结果。
5. 模型不能把“提出建议”当作“故障已解决”；结果由用户反馈决定。

### 5.3 诊断会话状态（MongoDB）

建议新增独立 `diagnosis_session` 集合，不向原 `chat_message` 表强塞所有诊断字段。

| 字段 | 用途 |
| --- | --- |
| `diagnosis_id` | 一次诊断的稳定 ID |
| `visitor_id` | 当前浏览器持有的匿名标识，供本地演示关联记录 |
| `device_id` / `device_model` | 已确认设备 |
| `original_problem` | 原始故障码或现象描述 |
| `status` | 当前生命周期状态 |
| `facts` | 已知故障事实（含用户回答） |
| `rounds` | 每轮问题、选项、用户选择、依据引用及时间 |
| `clarification_count` | 已完成澄清轮次，最大 3 |
| `result` / `feedback` | 最终建议、引用、用户是否解决 |
| `created_at` / `updated_at` | 时间与恢复排序 |
| `last_request_id` / `revision` | 去重与并发提交保护 |

建议状态：`in_progress` → `pending_verification`（已有建议待用户验证）、`insufficient`（资料不足）、`ended`（主动结束）；收到用户反馈后可进入 `resolved` 或 `unresolved`。在 `unresolved` 且尚有轮次与依据时，可根据 PRD 选择恢复 `in_progress`，不得突破 3 轮上限。

**事务边界**：先写入本轮结果与轮次，再向 SSE 发送诊断卡片；页面刷新后通过读取接口恢复，不依赖某条 SSE 是否被浏览器接收到。相同 `request_id` + 会话版本的重复提交不得推进两次。

### 5.4 SSE 行为

- `qa`：沿用 `progress`、`delta`、`final`，正常展示流式文字。
- `diagnosis`：推送 `progress`（检索、分析等），结构化完成时推送新的 `diagnosis` 事件，再推送 `final` 作为本次任务完成标记。
- **诊断动态选项不按 token 切成碎片展示**，而是一次发送校验后的 JSON。诊断仍具有实时进度感，也不需要浏览器拼接不完整 JSON。
- SSE 断线只能表明推送中断，**不能判定任务失败或丢失**；刷新后从 MongoDB 读取最终已保存结果。原进程内任务状态可先保留作运行时进度显示。

## 6. API 与数据契约（最小方案）

原则：继续使用现有 `/query` 执行普通问答和每轮诊断推理；为**查询历史、恢复诊断、用户反馈**增加必要的轻量接口。不增加一套独立的 `POST /diagnosis/infer` Pipeline。

| API（逻辑路径） | 用途 | 备注 |
| --- | --- | --- |
| `POST /query` | `mode=qa/diagnosis`；可带 `device_model`、`diagnosis_id`、本轮答案、`request_id` | 保持旧 qa 调用兼容，缺省 `mode=qa` |
| `GET /stream/{task_id}` | 推送问答 token、诊断处理进度和结构化结果 | 复用 SSE 基础设施 |
| `GET /status/{task_id}` | 查询任务状态 | **查询服务目前缺失，需修复** |
| `GET /history/{session_id}` | 查询普通聊天消息 | 沿用原接口 |
| `DELETE /history/{session_id}` | 删除普通聊天历史 | 修复当前 DELETE/GET 冲突 |
| `GET /diagnoses` | 列出当前匿名浏览器关联的诊断会话 | 受演示环境限制，不能视为安全认证 |
| `GET /diagnoses/{diagnosis_id}` | 刷新后读取已持久化的诊断状态与问题 | 恢复不可仅依赖流式队列 |
| `POST /diagnoses/{diagnosis_id}/feedback` | 设置已解决/未解决/待验证 | 不通过聊天文本猜状态 |
| `DELETE /diagnoses/{diagnosis_id}` | 删除一条诊断历史 | 配合前端二次确认 |
| `POST /upload` | 原文档导入，新增设备选择参数 | :8000 导入服务 |
| `GET /status/{task_id}`（导入） | 处理进度 | :8000 原接口 |
| `GET /documents` | 管理端基础文档列表 | 可建 Mongo 文档目录，不复刻完整文档 CMS |

上表是**逻辑接口约定**；实际在前端通过 `/api/qa/*`、`/api/admin/*` 代理转发，或选择一致的 `/api` 前缀。具体公开路径在实现前由 Codex 做一次映射检查，不以此表强制立即修改已有服务路由。

### 6.1 设备范围与可信引用必须在服务端执行

请求方提供的 `device_model` 只是用户意图，必须被服务端检查为受支持的设备；诊断会话恢复时以服务端保存的型号为准，不允许客户端任意变更。检索过滤也必须由服务端组装，不能只靠前端隐藏其他型号或 Prompt 提醒。

### 6.2 匿名用户的适用范围

V1 可以在 `localStorage` 保留随机、高熵的 `visitor_id`，后端按其关联历史，但**这不是认证**：知道标识的人可能尝试读取对应记录。只允许本地/受控演示，避免真实用户敏感数据；公开部署前至少需要加入访问保护、管理员鉴权、服务端速率限制，并审查跨域与上传文件大小/类型控制。

## 7. React 前端技术设计（D-06 已确认）

### 7.1 技术选型

- **React + Vite + TypeScript**：TypeScript 是本方案推荐的实现约定，用来约束诊断数据结构，避免选项卡片字段错位；不引入服务端渲染。
- **Tailwind CSS + shadcn/ui**：构建统一的布局、按钮、卡片、表单、对话框等；设计组件并不替代真实业务流程。
- **React Router**：基础页面导航；本期不必引入 Redux、复杂状态机库或 Next.js 服务端。
- **fetch + EventSource**：优先复用现有 HTTP/SSE 协议；仅在实际联调发现需要时补充网络管理库。

### 7.3 页面职责

| 路由建议 | 页面 | 主要行为 |

## 8. 可靠性、测试与验收门槛

### 8.1 最小必要修复（先于新业务）

1. 修正查询服务 `/status`、历史 DELETE 路由及与前端的调用不一致。
2. 修正诊断上下文需要的历史时间顺序；检查型号回填 TODO、异常路径中不存在的 logger。
3. 修正引用数据格式化不确定性；保证来源可在前端单独展示。
4. 为新增 API 设计可观测的错误状态和有限重试，不把失败包装为成功。
5. 核查原始资源与密钥是否适合公开 GitHub：课程代码来源、示例文档版权、`.env`/Token、MinerU 产物。

### 8.2 必须验证的关键场景

| 测试场景 | 通过标准 |
| --- | --- |
| 原普通问答回归 | 非流式/流式及历史行为不退化，必要时 Web MCP 正常使用 |
| 原导入回归 | PDF/Markdown 上传、解析、索引仍成功，失败可定位 |
| 设备范围约束 | 明确 K1，非 K1 资料不混入本地检索 |
| **诊断零联网** | 使用测试替身统计 MCP 调用次数，诊断所有路径均为 0 |
| 结构化动态诊断 | `ask` 支持一轮多题；回答整组提交；轮次最多 3 |
| 诊断中途刷新 | 重新读取已完成的轮次、问题、答案和状态 |
| 重复提交 | 同一 `request_id` 不生成两轮记录 |
| 引用与证据不足 | 引用 ID 属于本轮本地检索集合；无证据返回 `insufficient` |
| 安全与异常 | 不执行真实设备动作，模型异常、SSE 断线有可理解退路 |
| 完整 UI 联调 | 两个入口、历史、管理端可演示闭环 |

因为没有实体 3D 打印机，不能将软件测试通过写成“实际故障维修成功”。

## 9. 分阶段开发路线（仅规划，尚未授权执行）

| 阶段 | 工作范围 | 核心交付及停止条件 |
| --- | --- | --- |
| T0 基线与仓库整理 | 固定可运行基线、已知接口/历史/引用问题、公开仓库检查 | 原问答与导入仍可完整运行 |
| T1 设备数据与共用 RAG | 设备显式归属、上传关联、检索范围、`mode`、Web 守卫、条件路由 | K1 检索正确，qa 正常，诊断不调用 MCP |
| T2 动态诊断最小闭环 | 上下文整合、结构化决策/输出、Mongo 会话、SSE、恢复与反馈 | 1～3 轮动态问题、刷新恢复、重复提交不重复推进 |
| T3 React 产品前端 | 新建 Vite + TS + Tailwind + shadcn/ui，联通五个页面 | 用户/管理员主路径可点击、可演示 |
| T4 质量与展示 | K1 资料测试集、回归、README、来源说明、部署说明 | 功能和限制均可复核，面试能讲清“原有/新增” |

**粗略时间认知**：在环境仍能稳定运行、Codex 协助实现的情况下，T0～T2 可能需要数个有效开发日；完整 React UI 与回归会额外占用时间。未做本地测试前，不承诺具体天数。任何阶段失败时先修复当前问题，不自动扩大任务。

## 10. 待验证与明确不做的事

### 10.1 开发前由代码验证，不升级为新的产品决策

- K1 资料能否被导入且有足够章节/来源信息，是否需要额外维护文档目录表。
- 原图的 `item_name_confirm` 提前分支和并行状态合并，增量接入诊断后是否保持稳定。
- SSE 中断/重连后的结果读取、任务完成边界、上传处理进度的可恢复范围。
- React Dev Proxy 到 8000/8001 的映射与跨域问题；公开部署则另行审查权限配置。
- 现有向量索引内容是否混有课程测试资料；是否采用新知识集合重新导入 K1 数据。

### 10.2 不在 V1 额外建设

预设诊断树、诊断规则后台、多 Agent、缺陷照片识别、设备远程控制、用户注册/登录、跨设备同步、售后工单、复杂管理员权限、全站后端重构、生产级可用性架构。实际需要调整范围时必须先更新 PRD 和本设计文档。
