# PrintCare AI 开发计划

> 文档版本：V0.1｜日期：2026-10-09  
> 状态：**规划稿；未授权 Codex 执行代码开发**  
> 依据：`docs/01-产品需求文档.md`（PRD V0.3）、`docs/01A-产品决策记录.md`（D-01～D-06）、`docs/02-技术架构与改造方案.md`（V0.1）、仓库根目录 `AGENTS.md`（V1.0）。  
> 项目：基于课程项目“掌柜智库”的二次开发；原有能力和新增能力必须分别说明。

## 1. 计划目标与执行原则

本计划用于把已确认需求拆成**可独立实现、验证和回退**的小任务，而不是要求 Codex 一次性完成整个网站。

**V1 交付目标：** 在原有文档导入与 RAG 检索管线之上，完成 Creality K1 的普通知识问答和 RAG 驱动的动态交互式诊断，配备 React 用户端、基础管理端、历史记录和可核对的来源引用；能够以测试资料完成软件闭环演示。

**保持不变的边界：**

- 保留 MinerU／图片处理／文档切分／BGE-M3／Milvus／HyDE／RRF／Rerank 等既有能力；不新建第二套 RAG。
- 问答可以使用原有 MCP/Web 搜索；**诊断必须在调用前阻断联网搜索**，只用已导入、归属 K1 的可信本地知识。
- 不做人工诊断树；诊断动态生成问题与选项，每次最多 **3 轮澄清**，每轮 **1～3 个独立问题**、每题 **2～4 个选项**，可提前结束。
- 普通用户免注册，历史限当前浏览器关联；公开部署前必须另做访问保护，V1 以本地/受控演示为界。
- 前端选用 **React + Vite + TypeScript + Tailwind CSS + shadcn/ui**；优先保留后端两个 FastAPI 服务，通过代理统一前端入口。
- 不接入实体 3D 打印机，不声称经过实机维修验证；无授权的第三方文档不提交公开仓库。

**执行方式：** 一次只交付一个小任务或一个相互紧密依赖的小任务包；每次先确认改动范围，完成定向测试、回归、diff 检查和简短汇报，再由用户决定是否进入下一项。没有明确指令，Codex 不得自行提交、推送或执行破坏性操作。

## 2. 总体阶段路线

| 阶段 | 目的 | 阶段关键产物 | 进入下一阶段的门槛 |
| --- | --- | --- | --- |
| **T0 基线与仓库整理** | 固定已可运行的课程基底，修复必要接口与引用问题 | 基线验收记录、最小回归测试、已知风险清单 | 原上传与普通问答（含历史、SSE）可复核；仓库可公开内容已检查 |
| **T1 设备归属与共享检索** | 让现有 RAG 可靠地服务 K1，增加显式业务模式 | 设备归属、受约束检索、`mode` 路由、诊断 Web 禁用 | K1 本地证据归属正确、普通问答兼容、诊断 MCP 调用次数为 0 |
| **T2 动态诊断最小闭环** | 在共享检索链上加入可恢复的诊断流程 | 结构化决策、MongoDB 诊断会话、HTTP/SSE 契约、定向测试 | 3 轮上限、批量答题、引用校验、刷新恢复、重复提交保护通过 |
| **T3 React 产品前端** | 从课程演示页面升级为完整的用户/管理端体验 | 五个核心页面、交互组件、API/SSE 集成 | 用户从进入首页到查看诊断历史、管理员从上传到检索的演示可走通 |
| **T4 验收与项目展示** | 形成可投简历、可讲解、可复现的项目 | 固定 K1 测试集、回归结果、README、运行与演示说明 | PRD 验收场景覆盖并记录结果；区分原有/新增贡献及验证局限 |

这是一条**依赖顺序**而不是精确日历。阶段失败不自动跳阶段，不把“已编写代码”当成“已通过验收”。

## 3. 详细任务拆分

### T0 — 基线与仓库整理

**阶段目标：** 不影响已有能力的前提下，获得一套能反复验证的起点。不要在此阶段开始 React 重写或添加诊断逻辑。

| 任务 | 工作内容与主要位置 | 交付 / 验收 |
| --- | --- | --- |
| **T0-01 固定基线** | 核对当前 `main`、工作区状态、实际启动命令、依赖与服务端口；在本机复测文档上传、非流式问答、流式问答、历史读取 | 输出基线记录：环境、命令、真实结果、失败/未测项；不在记录中粘贴密钥 |
| **T0-02 修复最小接口问题** | `knowledge/api/query_router.py`、`services/query_service.py`、前端旧页面调用；检查查询 `/status/{task_id}` 缺失、历史删除 HTTP 方法错误 | `/status` 与现有前端请求一致；`DELETE` 正确清除目标会话；旧问答不退化 |
| **T0-03 修复历史与来源问题** | `utils/mongo_history_util.py`、`query_process/nodes/answer_output.py`、必要的测试；修复历史装配时间顺序、来源元数据格式化；核查设备名回填 TODO 与日志异常路径 | 对话上下文顺序正确；来源字段和原文对应；已有异常不再掩盖真正错误 |
| **T0-04 检查公开仓库** | README 草稿、`.gitignore`、已提交的 MinerU 中间产物和课程资料；仅审查、提出文件保留或清理建议 | 形成来源/授权/敏感信息清单；删除历史或改写提交必须另获明确授权 |

**T0 退出标准：** 原文档导入和问答可用，有可重复执行的基线验收过程；发现未修复的阻塞项时单独记录，不以“本机以前能跑”代替本轮实测。

### T1 — 设备归属与共享 RAG

**阶段目标：** 不复制检索链，让同一份 `reranked_docs` 可被普通问答与诊断使用。

| 任务 | 工作内容与主要位置 | 交付 / 验收 |
| --- | --- | --- |
| **T1-01 设备标识与导入归属** | 约定稳定 `device_id` / `device_model`，兼容原 `item_name`；管理员上传时由服务端校验设备并关联文档；局部修改 `import_process`、上传 API/Schema | K1 文档导入后有明确归属；用户传入伪造或不支持的型号被拒绝；不依赖 LLM 猜测归属 |
| **T1-02 受约束的本地检索** | 在 `item_name_confirm.py`、`vector_search.py`、`hyde_search.py` 等处复用现有过滤；确认设备选择贯穿到检索阶段 | 含 K1 与其他测试设备的隔离样本中，本地召回不混入其他型号；普通问答可用 |
| **T1-03 显式模式与图路由** | `query_schema.py`、`query_service.py`、`state.py`、`main_graph.py`；加 `mode=qa/diagnosis`，默认 `qa`；Rerank 后分流，正确处理设备未确认的提前退出 | 旧版无 `mode` 请求仍按普通问答执行；诊断能到达仅供后续开发使用的占位分支，不调用普通答案生成节点；此时不对外宣称诊断已可用 |
| **T1-04 诊断禁用联网** | 在 LangGraph 路由层**调用前**跳过 `web_search_mcp`，并加 Web 节点的防御性守卫；保留 `qa` 联网能力 | 使用 Mock/Spy 证明所有 `diagnosis` 路径 MCP 调用次数为 **0**；`qa` 路径未被误禁用 |
| **T1-05 规范证据对象** | 对 `reranked_docs` 提供薄层统一引用字段，不重写 RRF/Rerank 算法；整理 local/web 来源展示字段 | 本地资料可携带真实 `chunk_id`/标题/设备归属；没有的数据不伪造；前端可按来源类型渲染 |

**T1 退出标准：** 用已确认设备能取得受约束证据；普通 RAG 保持兼容；诊断本地检索与禁联网约束均有自动化验证。若需要迁移 Milvus Schema 或重建索引，先另行评审影响与回退方案。

### T2 — 动态诊断最小闭环

**阶段目标：** 先实现 API 可验证的诊断业务，再做漂亮的页面；一轮请求执行一次检索与诊断决策，不保持跨用户等待的长时运行图。

| 任务 | 工作内容与主要位置 | 交付 / 验收 |
| --- | --- | --- |
| **T2-01 结构化数据契约** | 新增 Pydantic 诊断请求/响应模型；至少有 `ask`、`answer`、`insufficient`，定义题目 ID、选项、引用、错误状态 | 合法样例可解析；超出题数、选项数、无效动作等被拒绝；前端不需从自由文本猜选项 |
| **T2-02 MongoDB 状态与幂等** | 新增 `diagnosis_session`；保存设备、原始问题、轮次、问题/答案、状态、引用与反馈；加 `request_id`/版本检查 | 刷新/进程重启后已提交进度可恢复；同一请求重复提交不重复增加轮次；失败不会标记完成 |
| **T2-03 多轮上下文装配** | 在服务层读取诊断会话、原始问题、已确认事实、本轮答案，形成完整检索问题；延用 `rewritten_query` 能力 | 第二轮“首层就脱落”不会丢失 K1/原始故障背景；已回答事实不被重复收集 |
| **T2-04 LLM 诊断决策** | 新增 `diagnosis_decision` 与轻量 `diagnosis_output`，由本轮 K1 `reranked_docs` 形成问题组或排查建议；提示词 + Pydantic 校验 + 有限重试 | 能产生 1～3 个独立问题、每题 2～4 选项；不足则 `insufficient`；达到第三轮后不能再问 |
| **T2-05 诊断来源与安全守卫** | 服务端校验诊断引用确属本轮真实本地检索结果，阻止无来源维修建议；高温/电气/拆机等风险用保守退路 | 伪造引用、跨型号引用、无检索结果不能形成有操作指令的 `answer`；不调用 Web MCP |
| **T2-06 HTTP/SSE 与反馈** | 沿用 `POST /query`、`/stream`，新增 `diagnosis` 结构化事件、诊断列表/详情/反馈/删除等必要接口；选项通过 HTTP 提交 | SSE 只推送**已校验并持久化**的题目；用户反馈能区分已解决/未解决/待验证；断线后能从 Mongo 读取结果 |
| **T2-07 最小业务验收** | 用 Mock 设备文档及少量合法 K1 测试资料，执行 API 级多轮测试与负面测试 | 至少完成一次连续三轮（或提前结束）闭环，覆盖 `ask/answer/insufficient`、重试、断线、幂等与 3 轮限制 |

**T2 退出标准：** 不依赖 React 页面，通过 API/脚本即可验证“描述故障 → 本地检索 → 动态问题组 → 批量选择 → 建议或不足 → 反馈/历史”。不能把模型文本出现“引用”视为引用校验已通过。

### T3 — React 全栈产品前端

**阶段目标：** 利用已经稳定的 API 完成真实产品交互；视觉设计优先于无关的新业务功能，但不在这一阶段重写后端。

| 任务 | 工作内容 | 交付 / 验收 |
| --- | --- | --- |
| **T3-01 前端工程底座** | 新建 `frontend/`：React、Vite、TypeScript、Tailwind、shadcn/ui、路由、环境变量和 `/api` 代理、统一 HTTP/SSE 客户端 | 能分别连通查询服务 8001 与导入服务 8000；不在组件中散落硬编码 URL |
| **T3-02 设计系统与工作台** | 导航、排版、反馈组件；K1 设备卡片；“知识问答/智能诊断”双入口 | 桌面端主要路径明确，移动端可基本操作；不出现自动分流入口 |
| **T3-03 知识问答页面** | 流式聊天、不同来源的引用卡片、处理中/无资料/失败状态、会话历史 | 普通问答完整闭环；MCP 来源可区分；旧问答关键场景回归通过 |
| **T3-04 智能诊断页面** | 故障输入；逐轮 1～3 题的结构化卡片；批量提交；进度、建议、引用、结果反馈 | 不解析自由文本充当选项；三轮上限与继续/结束行为清晰；禁重复提交 |
| **T3-05 历史与恢复页面** | 当前浏览器匿名记录、问答/诊断分类、详情、继续、删除确认 | 刷新后能恢复已保存的诊断；反馈状态在列表与详情一致；不宣称跨浏览器同步 |
| **T3-06 基础知识库管理** | 文档上传、K1 归属、导入状态/错误、基础文档列表和重复文件提示 | 管理端可完成“上传 → 可见进度 → 资料可查询”；管理员入口仅限受控演示环境，公开前须补保护 |
| **T3-07 交互与可用性检查** | 空白态、加载态、错误态、基础键盘支持、响应式与浏览器检查 | 五个页面可连贯操作，无阻塞级 UI 错误；旧 HTML 保留直至新前端验收完成 |

**T3 退出标准：** 可以从首页进入普通问答和诊断，执行完整用户闭环；可以从管理端上传资料并验证检索。前端美化不得掩盖错误或假装后端已执行完成。

### T4 — 质量验收、README 与展示

| 任务 | 工作内容 | 交付 / 验收 |
| --- | --- | --- |
| **T4-01 K1 资料与固定测试集** | 选用有权使用的设备文档和自行编写的测试输入；区分故障码、打印异常、资料不足与危险场景 | 测试用例记录输入、预期类型、文档来源、实际输出；第三方资料按授权情况处理 |
| **T4-02 完整回归与异常测试** | 对照 PRD AC-01～AC-13，执行导入、QA、诊断、断线/重复请求和引用校验测试 | 输出逐项 Pass/Fail/Not Run 与证据；失败项不隐瞒、不用降低标准掩盖 |
| **T4-03 README 与可复现运行** | 写清原课程来源、PrintCare 自主新增部分、环境依赖、启动/关闭、演示入口、已知限制 | 旁人按文档有合理机会复现软件演示；不上传密钥和未授权资料 |
| **T4-04 面试展示材料** | 准备 2～3 分钟产品演示顺序、核心流程图、关键改造解释、已知权衡与测试结果 | 能回答“原项目已有何能力、我新增了什么、为什么这样设计、怎样验证” |

**T4 退出标准：** 软件可演示且有实际测试记录；能够清楚解释技术边界，不把模拟故障案例说成实机成功率。

## 4. 跨阶段质量关口（不可绕过）

1. **RAG 回归关口：** T0/T1/T2/T3 的每次核心修改后，都至少跑受影响的问答/导入定向测试；阶段验收必须包含普通问答回归。
2. **联网隔离关口：** 诊断 `mode` 时 Web MCP 调用次数为 0，不能只通过 UI 隐藏联网开关或通过 Prompt 声明禁用。
3. **证据真实性关口：** 诊断引用必须来自本轮命中的本地 K1 文档，字段缺失不伪造；没依据时 `insufficient`。
4. **状态真实性关口：** MongoDB 是诊断历史与恢复的数据来源，SSE/内存任务表只负责运行时通知；重复提交不得重复推进。
5. **范围控制关口：** 不新增账号、人工诊断树、第二套 RAG、多 Agent、设备控制，也不为 UI 开发大规模合并后端。
6. **公开仓库关口：** 验证文件授权和敏感内容；若清理已提交的历史内容，应事先单独批准操作方案。

## 5. Codex 单任务工作模板（后续使用，并非现在执行）

后续派发任务时，建议每轮用一个简短模板，避免把整份开发计划复制进提示词：

```text
任务编号：T?-??
目标：完成本任务对应的最小可验证成果。
依据：根目录 AGENTS.md、docs/01-产品需求文档.md、
      docs/02-技术架构与改造方案.md、docs/03-开发计划.md。
范围：仅任务涉及的文件；若需扩大范围，先说明并请求确认。
实现：优先复用既有实现；不额外重构、不自行扩需求。
验证：执行本任务定向测试 + 受影响功能回归；报告未运行项及原因。
交付：修改摘要、文件列表、执行过的命令及结果、风险/阻塞项。
限制：除非本轮明确授权，不 commit、不 push、不执行破坏性命令。
```

每个任务完成后由用户决定：**验收通过 / 需要返工 / 暂停并重新设计**。必要时更新技术文档；已确认产品行为变动必须先更新 PRD 和决策记录。

## 6. 时间、优先级与可推迟项

**优先级：** T0 → T1 → T2 构成“有技术差异的最小后端产品”；T3 形成完整全栈展示；T4 形成可交付作品。不要为了视觉完成度过早跳过后端诊断与引用可靠性验证。

时间不写成固定交付日期。实际耗时受原项目环境、模型调用、K1 文档质量、Milvus 数据隔离和 UI 完成度影响；每个阶段完成后再估算剩余任务。若进度超预期，应先缩小**非核心展示细节**，不降低 3 轮上限、诊断禁联网、引用校验、状态持久化等已确认要求。

**可推迟但不可假装已实现：** 多型号正式上线、文档版本对比、精细化检索评估看板、照片诊断、跨设备历史同步、生产级权限管理、售后工单。
