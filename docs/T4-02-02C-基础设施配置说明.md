# T4-02-02C 基础设施配置说明

盘点日期：2026-10-13。本说明基于用户提供的实际 Linux VM `docs/docker-compose.yml` 静态审阅；本轮未连接 VM、读取关联密钥文件或执行任何 Docker 命令。无密钥复用版本见 `docs/docker-compose.example.yml`；原始文件保留在工作区供核对，**不得提交**。该示例仅用于本地或受控开发环境，不代表已具备公网部署安全性。

## 实际 Compose 拓扑

| 服务 | 实际镜像与职责 | 对外端口 | 数据与依赖 |
| --- | --- | --- | --- |
| `etcd` | `quay.io/coreos/etcd:v3.5.25`；Milvus 元数据存储 | 无 | `${DOCKER_VOLUME_DIRECTORY:-.}/volumes/etcd:/etcd`；带健康检查 |
| `minio` | `minio/minio:RELEASE.2024-12-18T13-15-44Z`；Milvus 对象存储及应用导入原文件存储 | 9000（S3 API）、9001（控制台） | `${DOCKER_VOLUME_DIRECTORY:-.}/volumes/minio:/minio_data`；带健康检查 |
| `standalone` | `milvusdb/milvus:v2.5.5`；K1 向量 Collection 与混合检索 | 19530（Milvus）、9091（健康端点） | `${DOCKER_VOLUME_DIRECTORY:-.}/volumes/milvus:/var/lib/milvus`；依赖 `etcd`、`minio`，使用 Rocksmq |
| `attu` | `zilliz/attu:v2.5.10`；Milvus 运维 GUI，不是业务运行时依赖 | 7000 | 容器内连接 `standalone:19530`；依赖 `standalone` |
| `mongodb` | `mongo:7.0`；问答历史和诊断会话持久化 | 27017 | 两个宿主机挂载目录：`volumes/mongodb/data`、`volumes/mongodb/config`；带健康检查 |

五个服务均使用默认网络 `milvus`，并设置 `restart: always`。原配置中的 `depends_on` 只保证启动顺序，未以健康状态阻塞后续服务；实际复现时应在启动后确认各健康检查和端口可达，不能仅以容器已创建认定就绪。

## 与 Windows 后端的连接映射

后端不在 Compose 中运行，Windows 主机通过 `knowledge/.env` 连接 VM。以下为格式，不填写真实 IP、域名或密码：

| 后端变量 | 对应 Compose 服务 | 形式与注意事项 |
| --- | --- | --- |
| `MILVUS_URL` | `standalone` 19530 | `http://<vm-host>:19530`；由 `StorageClients.get_milvus_client()` 使用。 |
| `MONGO_URL`、`MONGO_DB_NAME` | `mongodb` 27017 | `mongodb://<vm-host>:27017` 与本地指定库名；当前原 Compose 未配置 MongoDB 认证，不能把端口直接暴露至不受控网络。 |
| `MINIO_ENDPOINT`、`MINIO_ACCESS_KEY`、`MINIO_SECRET_KEY`、`MINIO_BUCKET_NAME` | `minio` 9000 | 地址格式为 `<vm-host>:9000`，不含协议；当前代码固定 `secure=False`，必须使用受控网络中的 HTTP 或另行调整实现。Compose 的 MinIO 访问密钥与后端变量必须一致。 |
| 无业务变量 | `minio` 9001、`standalone` 9091、`attu` 7000 | 分别用于 MinIO 控制台、Milvus 健康检查和 Attu；不应由前端直接持有基础设施凭据。 |

Vite 仅代理浏览器请求到 Windows 上的查询服务 8001 和导入服务 8000；不直接代理上述 VM 端口。

## 脱敏与可移植处理

原 Compose 在 MinIO 服务中包含了明文访问密钥和默认式弱口令值，不能纳入版本控制。`docs/docker-compose.example.yml` 忠实保留了服务拓扑、镜像版本、端口、命名网络、健康检查、挂载结构和 `security_opt`，仅将两项 MinIO 凭据替换为必填的环境变量插值。

示例配置保留 `DOCKER_VOLUME_DIRECTORY`：未设置时数据会落在运行 Compose 目录下的 `volumes/`；新 VM 可在本机忽略的环境文件中将它设为预先准备的数据目录。不得把已有 VM 的数据目录、卷内容或任何密钥复制进仓库。原配置未发现固定 IP 或绝对主机路径；端口映射仍默认监听 VM 所有接口，需以 VM 防火墙/受控网络限制访问。

建议在与示例 Compose 同目录创建且不提交的 `.env`，至少设置：

```ini
MINIO_ACCESS_KEY=choose-a-non-default-local-access-key
MINIO_SECRET_KEY=choose-a-long-local-secret
# 可选：DOCKER_VOLUME_DIRECTORY=/srv/printcare-infra
```

这不是 `knowledge/.env` 的替代品：Windows 后端仍需自己的忽略文件，并以同一组 MinIO 凭据和 VM 可达地址配置连接。

## 启动、初始化与业务知识的边界

1. **Compose 启动：** Linux VM 需安装 Docker Engine 与 Compose 插件，并准备可写的数据目录、端口策略和上述不提交的变量文件。后续获准操作时，使用无密钥示例从其所在目录启动；本轮没有执行启动命令。
2. **MongoDB/MinIO 初始化：** 当前没有独立 bootstrap。MongoDB 会在业务首次写入时形成 `chat_message`、`diagnosis_session` 等集合，诊断仓储随后创建索引。MinIO 客户端第一次使用时会检查并在不存在时创建 `MINIO_BUCKET_NAME`。这些行为需要后端凭据和连通性，不能由 Compose 取代。
3. **Milvus Collection：** `knowledge/processor/import_process/nodes/import_milvus.py` 和 `nodes/item_name_recognition.py` 在受控导入首次需要时创建 K1 chunk 与 item-name Collection、Schema 和索引。不要为初始化而删除或重建现有 Collection。
4. **K1 知识导入：** 容器正常不等于已有可检索资料。另需以管理员身份、合法来源的 K1 PDF/Markdown 经现有导入图处理；仓库没有可再分发的生产种子数据或独立迁移脚本。

## 仍不能独立复现的部分

- 实际 VM 的网络地址、DNS/防火墙、Docker/Compose 版本、容器现况和持久化数据状态未在本轮连接验证。
- 原 Compose 没有 MongoDB 认证、TLS、对外端口收敛或备用 MinIO 凭据轮换配置；它适用于受控演示基础设施，不应直接等同生产安全方案。
- 缺少经干净 VM 实测的启动记录、完整后端模型/LLM 配置、可再分发 K1 数据和独立 Collection 初始化工具。
- T3 的真实 `answer → pending_verification → resolved/unresolved` 前端回归及活跃 SSE 物理断连恢复仍未完整验收；基础设施容器可启动不改变此结论。
